YUME Stealth transport, built for embedding.

YUME carries TCP, UDP, and packet traffic inside a persistent, browser-shaped connection. The client yume and the daemon yumed speak YTP/1, and an experimental C ABI embeds the same runtime in other programs.

yume and yumed speak YTP/1 and read schema-1 configuration. Transport v2, the protocol before it, has been removed. Product, wire, configuration, and ABI versions are independent.

Tested paths and open release gates are in the implementation status.

Client and daemon

The native programs carry SOCKS5 CONNECT and UDP ASSOCIATE, local forwards, direct TCP and UDP routes, and a managed Linux TUN, behind admission and a static cover site.

Experimental C ABI

The opt-in libyume runs the same native endpoint and carries authenticated named streams, named packets, and routed TCP and UDP. Its interface is not frozen.

Modules

yumed starts configured module programs and hands each one its service's streams over a private UNIX socket. Chat, file, and codec modules are planned on libraries that already exist.

Remaining work

Complete-session stealth, classifier, WAN, and soak qualification, the reverse-proxy cover, packaged service qualification, and the GUI and Android phases.

Install

YUME builds from source on Linux x86-64. Add --tests to build the test executables.

Other surfaces

GUI, Android, and embedding

The desktop GUI source waits for a native interface and does not build yet. Android is maintained in a separate repository. Applications using the experimental C ABI must track its changing interface until the functional, lifecycle, and installation gates pass.

C ABI Implementation status

Tunnel protection

Authentication, admission, and authorization are separate checks, and each one fails closed.

Layer YTP/1
Client identity A composite Ed25519 + ML-DSA-87 identity per client, and explicit trust in the server's composite identity. Both signatures must verify. Admin will need a second, distinct identity from a separate store, and that exchange is not implemented yet.
Key establishment ML-KEM-1024 + X25519 + a distinct 32-byte access PSK per client identity, with roles, identities, transcript, capabilities, parameters, and the TLS exporter bound into the key schedule.
Record layer One-use directional AES-256-GCM keys. A direction rekeys after 1 MiB, 512 records, or 500 ms checked on the next send. Streams and the connection have credit, and allocation limits apply before attacker-controlled work.
Policy surface No security modes and no suite negotiation. Named service capabilities are authenticated, and every OPEN is authorized and bounded on its own.
Carrier Persistent TLS 1.3 + HTTP/2 + WebSocket on one connection, shaped by one immutable captured browser profile. A default-off capability in the pinned OpenSSL reproduces the profile's ClientHello structure.
Admission and cover An exporter-bound, replay-protected HMAC proof promotes a connection. A missing or invalid proof gets the static cover site and no YUME-shaped response. A reverse-proxy cover is not implemented yet.

Whole-session browser comparisons, classifiers, WAN tests, and soak qualification remain open. yumed terminates the tunnel and sees the authenticated client and destination. Application TLS can protect content end to end. Read the stealth model and the threat model before deploying it.

Build, provision, connect

The quick start walks through these steps. Credentials are owner-only files, and a client bundle must move to its machine through a trusted channel.

01

Build

Clone the tree and run ezbuild.sh.

02

Provision

yume-setup writes a server and client kit: identities, access PSK, admission key, TLS material, configuration, and a cover site.

03

Serve

yumed serves the cover site and the authenticated tunnel on one listener.

04

Connect

The client offers SOCKS5, local forwards, or a managed Linux TUN.

Build

git clone https://github.com/FixCraft-Inc/yume.git
cd yume
./ezbuild.sh

Provision

python3 tools/yume_setup.py init \
    --host yume.example.com --port 8443 \
    --output ~/yume-kit --client-name laptop

Server

./build/bin/yumed --config ~/yume-kit/server/yumed.json --validate
./build/bin/yumed --config ~/yume-kit/server/yumed.json

Client

./build/bin/yume --config ~/yume-kit/client/yume.json
curl --socks5-hostname 127.0.0.1:1080 https://example.com/

The kit's development CA and static cover do not make a public endpoint credible. Choose cover content and TLS trust deliberately before exposing a server.

Port 443 needs CAP_NET_BIND_SERVICE, which the packaged service grants and nothing more. Cloudflare in HTTP mode terminates TLS and breaks YUME. Use Spectrum or another TCP passthrough if you front the daemon with it.

Verify release files

Published artifacts carry SHA-256 sidecars, an aggregate SHA256SUMS.txt, and a machine-readable manifest. Detached GPG signatures are attached when signing secrets are configured, and the workflow verifies each signature before uploading it.

Checksums

Verify with the per-artifact .sha256 file or the aggregate list.

Aggregate
sha256sum -c SHA256SUMS.txt

Signatures

Signed builds ship .sig sidecars for both artifacts, the checksum list, and the manifest.

GPG
gpg --verify yumed-amd64-linux.sig yumed-amd64-linux

Manifest

release-manifest.json records each artifact's component, OS, architecture, size, linkage, and SHA-256. Its signature fields remain empty because the current workflow creates it before signing.
