Current boundary

YUME is experimental development software with a deliberate coexistence boundary: keep the tunnel useful while rebuilding its internals.

Development line {{ site.product_version }}: no stable release published

The default build produces the runnable 0.2 yume and yumed tunnel. YTP/1, the dependency-clean session engine, schema 1, and the replacement ABI are built alongside it, but they do not yet form an authenticated end-to-end tunnel.

Breaking the new wire and schema is acceptable during development; deleting working behavior before its replacement reaches parity is not. Exact implementation and evidence limits are in the implementation status.

Runnable product

The 0.2 client and daemon retain SOCKS, forwards, packet routing, composite authentication, profile-matched TLS/H2 ingress, and a real cover backend while the replacement matures.

Foundation retained

The tree includes bounded YTP/1 codecs, the session engine, opt-in hybrid security, TLS 1.3, duplex H2 carrier, TCP ByteChannel, and direct-route providers, strict schema-1 configuration, setup and doctor tools, layering checks, and build-tree ABI consumers.

Still unwired

The provider candidates are not connected to a live YTP/1 endpoint. The build-tree ABI can carry authenticated transport-v2 named streams, but schema 1 still needs a genuine front door, admission and provider composition, runtime adapters, stream and packet wiring, and full security qualification.

Switch-over rule

Transport-v2/AUTH-v2 is incompatible with YTP/1 by design. The old runtime leaves the default only after tunnel, cover, routing, embedding, packaging, and qualification parity.

Install

YUME builds from source on Linux x86-64. The default build keeps the runnable tunnel and also compiles the modular foundation for focused tests. Full builds use the pinned transport dependencies recorded by the tree.

Tunnel protection

The replacement keeps YUME's hybrid, fail-closed identity while tightening per-client transport credentials, service policy, and resource contracts.

Layer Runnable 0.2 transport YTP/1 replacement contract
Client identity Composite Ed25519 + ML-DSA-87; both signatures verified. Admin requires a second, distinct identity from a separate admin store. Per-client composite transport identity plus explicit trust in the server's composite public identity; every required component must verify.
Key establishment ML-KEM-1024 + X25519 + a random pre-shared key, bound to the TLS exporter. ML-KEM-1024 + X25519 + a distinct access PSK per client identity, with exact roles, identities, transcript, capabilities, parameters, and exporter bound into the schedule.
Record layer One-use AES-256-GCM keys per message, with independent directional epochs. One-use directional keys, bounded rekey work, 31-bit streams, connection and stream credit, and allocation limits before attacker-controlled work.
Policy surface Default Extreme: 256 KiB, 512 DATA frames, or 500 ms of sender activity. Authenticated Normal, Soft, and bounded Ultimate policies widen the active epoch for less hybrid-rekey overhead. No security-mode switch or suite negotiation in YTP/1. Named service capabilities are authenticated, then every OPEN is independently authorized and bounded.
Carrier Persistent TLS 1.3 + HTTP/2 + WebSocket on one connection, using one immutable captured profile. The default native backend uses an opt-in capability in the pinned OpenSSL source to reproduce the fixture's ClientHello structure. TLS 1.3 secure channel and genuine duplex HTTP/2 carrier, separated from the engine and from independently versioned browser-profile evidence.
Admission and cover Keyed active-probe admission gates AUTH; a supervised loopback cover site answers ordinary requests on the same listener. Cheap replay-protected admission promotes only valid traffic. Invalid or absent admission continues as ordinary website or reverse-proxy traffic with no YUME-shaped response.

Evidence, not slogans. YUME can raise the cost of blocking and reduce some metadata exposure. It is not impossible to block, immune to stateful DPI, or identical to a browser. Existing 0.2 captures do not automatically qualify the replacement provider; resumed sessions, same-session comparisons, carrier semantics, timing and volume, classifier testing, and deployed soak remain separate gates. yumed is a terminating single-hop proxy, not an onion relay: the server sees traffic as it exits. Read the stealth model and the threat model before deploying it.

Build, provision, connect

This workflow is the runnable transport-v2 path. yume-setup init generates its server and client kit. Admission and inner-PSK files carry no group or world permission bits and must be distributed out of band.

01

Build

Clone the tree and run ezbuild.sh.

02

Provision

Generate composite identities, the admission secret, the inner PSK, and TLS material.

03

Serve

yumed shares one listener between the loopback cover backend and the authenticated H2 tunnel.

04

Connect

Clients use SOCKS or local and reverse forwarding, depending on the job.

Build

git clone https://github.com/FixCraft-Inc/yume.git
cd yume
./ezbuild.sh

Server

sudo ./build/bin/yumed \
    --listen 443 \
    --cert certs/server.crt --key certs/server.key \
    --auth-keys /etc/yume/authorized_keys \
    --obfs-secret-file /etc/yume/secrets/admission.hex \
    --inner-psk-file /etc/yume/secrets/inner.hex \
    --real-backend loopback://127.0.0.1:3000

Client

./build/bin/yume \
    --server yume.example.com \
    --auth ~/.yume/id_ed25519 \
    --obfs-secret-file ~/.config/yume/admission.hex \
    --inner-psk-file ~/.config/yume/inner.hex \
    --profile chrome \
    --socks 127.0.0.1:1080

The separate yume-setup-ytp1 and yume-doctor-ytp1 commands exercise experimental schema-1 provisioning. Their kits do not drive the current yume or yumed binaries.

Binding port 443 needs sudo or cap_net_bind_service. Cloudflare in HTTP mode terminates TLS and breaks YUME. Use Spectrum or another TCP passthrough if you front the daemon with it.

Verify release files

Published artifacts carry SHA-256 sidecars, an aggregate SHA256SUMS.txt, and a machine-readable manifest. Detached GPG signatures are attached when signing secrets are configured, and the workflow verifies each signature before uploading it.

Checksums

Verify with the per-artifact .sha256 file or the aggregate list.

Aggregate
sha256sum -c SHA256SUMS.txt

Signatures

Signed builds ship .sig sidecars for both artifacts, the checksum list, and the manifest.

GPG
gpg --verify yumed-amd64-linux.sig yumed-amd64-linux

Manifest

release-manifest.json records each artifact's component, OS, architecture, size, linkage, and SHA-256. Its signature fields remain empty because the current workflow creates it before signing.
