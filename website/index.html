YUME

Yume Universal Multiprotocol Engine. YUME tunnels TCP and UDP through one persistent TLS 1.3 + HTTP/2 + WebSocket connection shaped like ordinary browser HTTPS, with mandatory ML-KEM-1024 + X25519 + random-PSK key establishment, per-message AES-256-GCM keys, and independent directional epochs. The client (yume) and daemon (yumed) build from one tree.

Where this actually stands

YUME 0.2.0-dev6 is experimental software implementing an incompatible dev6 transport contract. This page describes what exists in the tree, not what is promised.

Development line - no 0.2.0 release published

The release workflow refuses to publish unless an independent security review is complete and the documented lifecycle, scale, soak, WAN, and same-session gates are approved. None of those are signed off yet, so the supported way to run YUME today is to build this tree.

No 0.2.0 release-qualified transport throughput or latency result has been published. The older public WAN run used 1.x and does not describe the current transport; treat it as a historical datapoint only. Current development measurements and their limits are tracked in WAN behavior and release gate.

Existing evidence

The historical Linux x86-64 yume / yumed command-line slice with its explicitly selected Go TLS helper; that evidence does not qualify the new native default.

In progress

The desktop GUI has earlier Linux/X11 lifecycle evidence but the current native candidate still needs a fresh consumer gate. Android has earlier 0.2.0-dev6 non-connected ARM64 evidence, but it is not synchronized to the current candidate; its connected VPN, routing, leak-policy, and release gates remain open.

Not qualified

macOS, Windows, and embedded targets. They are not part of the 0.2.0 surface and are not published here.

Explicitly disabled

Remote command execution. Policy and wire inputs are reserved, but direct and relayed execution fail closed.

Install

YUME builds from source on Linux x86-64. Full builds use the checksum-pinned, patched OpenSSL 3.5.7 because the native Chrome emitter needs its default-off extension and composite identities need ML-DSA-87; they also need nghttp2 1.64 or newer.

GUI, Android, and embedding

The desktop GUI (yume-gui) is a Dear ImGui + GLFW application in the same tree, off by default. It drives the same in-process client runtime as the CLI through the shared facade library, but it is still a development preview - the CLI remains the supported automation surface. The Android client and any third-party embedder go through libyume, the stable C ABI, whose compatibility rules are documented separately.

What protects the tunnel

Every layer below is mandatory in 0.2.0-dev6. There is no public-key-only mode, no plaintext fallback, and no flag that downgrades the wire.

Layer 0.2.0-dev6
Client identity Composite Ed25519 + ML-DSA-87; both signatures verified. Admin requires a second, distinct identity from a separate admin store.
Key establishment ML-KEM-1024 + X25519 + a random pre-shared key, bound to the TLS exporter.
Record layer One-use AES-256-GCM keys per message, with independent directional epochs.
Rekey policy Default Extreme: 256 KiB, 512 DATA frames, or 500 ms of sender activity. Authenticated Normal, Soft, and bounded Ultimate policies widen the active epoch for less hybrid-rekey overhead.
Carrier Persistent TLS 1.3 + HTTP/2 + WebSocket on one connection, using a single immutable Chrome 151 transport profile. The default native backend uses a default-off patch on pinned OpenSSL 3.5.7 for browser-shaped GREASE, extension permutation, key shares, point formats, and certificate compression.
Admission Keyed active-probe admission. Public-node startup requires an obfs secret; unauthenticated and malformed paths never reach AUTH.
Cover traffic A separate supervised Node.js 24 site bound to loopback answers ordinary browser requests on the same listener.

What this is not. YUME raises the cost of blocking and can reduce metadata exposure depending on the route. It is not impossible to block, not immune to stateful DPI, and not identical to Chrome on the wire. The default openssl-chrome151 backend closes the six pinned ClientHello structure rows, but resumed sessions, same-session browser comparison, full carrier behavior, traffic timing/volume, classifier testing, and deployed soak are separate gates. The older helper's evidence does not automatically qualify the native replacement. yumed is a terminating single-hop proxy, not an onion relay: the server sees traffic as it exits. Read the stealth model and the threat model before deploying it.

Running it

Both secret files hold exactly 64 lowercase hex characters (32 random bytes), carry no group or world permission bits, and must be distributed out of band. yume-setup init generates the whole server and device kit if you would rather not do it by hand.

01

Build

Clone the tree and run ezbuild.sh.

02

Provision

Generate composite identities, the admission secret, the inner PSK, and TLS material.

03

Serve

yumed shares one listener between the loopback cover backend and the authenticated H2 tunnel.

04

Connect

Clients use SOCKS or local and reverse forwarding, depending on the job.

Build

git clone https://github.com/FixCraft-Inc/yume.git
cd yume
./ezbuild.sh

Server

sudo ./build/bin/yumed \
    --listen 443 \
    --cert certs/server.crt --key certs/server.key \
    --auth-keys /etc/yume/authorized_keys \
    --obfs-secret-file /etc/yume/secrets/admission.hex \
    --inner-psk-file /etc/yume/secrets/inner.hex \
    --real-backend loopback://127.0.0.1:3000

Client

./build/bin/yume \
    --server yume.example.com \
    --auth ~/.yume/id_ed25519 \
    --obfs-secret-file ~/.config/yume/admission.hex \
    --inner-psk-file ~/.config/yume/inner.hex \
    --profile chrome \
    --socks 127.0.0.1:1080

Binding port 443 needs sudo or cap_net_bind_service. Cloudflare in HTTP mode terminates TLS and breaks YUME - use Spectrum or another TCP passthrough if you front the daemon with it.

Verifying a release

Published artifacts carry SHA-256 sidecars, an aggregate SHA256SUMS.txt, and a machine-readable manifest. Detached GPG signatures are attached when signing secrets are configured, and the workflow verifies each signature before uploading it.

Checksums

Verify with the per-artifact .sha256 file or the aggregate list.

Aggregate
sha256sum -c SHA256SUMS.txt

Signatures

Signed builds ship .sig sidecars for both artifacts, the checksum list, and the manifest.

GPG
gpg --verify yumed-amd64-linux.sig yumed-amd64-linux

Manifest

release-manifest.json records each artifact's component, OS, architecture, size, SHA-256, and signature sidecar.
