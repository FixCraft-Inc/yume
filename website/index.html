YUME

An open-source transport that carries TCP and UDP through TLS 1.3 sessions shaped like ordinary Chrome HTTPS, with hybrid ML-KEM-768 + AES-GCM inner crypto and optional live key hopping. Both client (yume) and daemon (yumed) build from one tree and run on hardware from a 128 MiB OpenWRT router up to a server.

How it works

Three independent layers of byte-shape camouflage on top of TLS 1.3, plus end-to-end inner crypto. Each layer is on by default and can be turned off independently.

Real TLS 1.3, browser fingerprint

OpenSSL emits a real ClientHello configured to match Chrome 135 / Firefox 126 / Safari 17, so JA3 / JA4 fall in the browser cluster. Switch profiles with --profile.

HTTP/2 carrier handshake

After TLS the client emits a real PRI * HTTP/2.0 preface, Chrome-shaped SETTINGS, and a HEADERS frame for a POST /<token>/<nonce> with a Chrome user-agent. To stateless DPI it's a Chrome → CDN gRPC-web request.

Real HTML facade

A browser hitting the same hostname with GET / gets back the configured HTML page. YUME clients and browsers cohabit on port 443.

Hybrid post-quantum inner crypto

ML-KEM-768 KEM + AES-256-GCM AEAD via BaseFWX, with optional Argon2id heavy KDF and 1–4 Hz live key hopping. End-to-end inside the TLS tunnel.

Anonym mode

--anonym strips logs (no client hostname, no IP, no auth line). The server can prove no-log compliance to the client via local CA-signed chain or a remote API.

Three-layer permission gate

Dangerous features (LAN bridging, server-side exec, unrestricted control) need a build switch and a runtime flag and a per-key allow entry. Stock builds physically can't do them.
