YUME Stealth transport, built for embedding.

YUME carries TCP, UDP and IP packets inside one connection shaped like Chrome loading a website. Anyone without the key gets an ordinary site. Clients with it get a post-quantum authenticated tunnel. The same engine runs as the yume client, the yumed server and a C library for other programs.

How it works

Every byte is sealed by YTP/1 first, then wrapped in the same layers a browser uses. A watcher sees an HTTPS visit. The server sees an authenticated client.

Client and server

yume takes traffic from SOCKS5 (TCP and UDP), local forwards or a managed Linux TUN device. yumed serves the cover site and the tunnel on one port, and opens only the destinations its policy allows.

C library

The opt-in libyume runs the same endpoint inside another program: authenticated named streams, packet channels, and routed TCP and UDP.

Circuits

TCP connections can leave through two or three servers in one operator's cluster, with separate protection on every hop.

Modules

yumed hands a service's streams to a module program over a private UNIX socket. Chat, file and codec modules are planned on libraries that already exist.

The implementation status lists what each part is tested with.

YUME builds from source on Linux x86-64. Add --tests to build the test executables.

Other surfaces

GUI, Android, and embedding

The Linux desktop GUI imports kits and starts, stops and watches clients through their control sockets. Build it with -DYUME_BUILD_GUI=ON. The Android client lives in its own repository and runs native YTP/1 through the C library's device bridge. Programs that embed the C library build against the same source tree, and its interface can still change between development versions.

Tunnel protection

Authentication, admission, and authorization are separate checks, and each one fails closed.

Layer YTP/1
Client identity A composite Ed25519 + ML-DSA-87 identity per client, and explicit trust in the server's composite identity. Both signatures must verify.
Key establishment ML-KEM-1024 + X25519 + a distinct 32-byte access PSK per client identity, with roles, identities, transcript, capabilities, parameters, and the TLS exporter bound into the key schedule.
Record layer One-use directional AES-256-GCM keys. A direction rekeys after 1 MiB, 512 records, or 500 ms checked on the next send. Streams and the connection have credit, and allocation limits apply before attacker-controlled work.
Policy surface No security modes and no suite negotiation. Named service capabilities are authenticated, and every OPEN is authorized and bounded on its own.
Carrier Persistent TLS 1.3 + HTTP/2 + WebSocket on one connection, shaped by one immutable captured browser profile. A default-off capability in the pinned OpenSSL reproduces the profile's ClientHello structure.
Admission and cover An exporter-bound, replay-protected HMAC proof promotes a connection. A missing or invalid proof gets the static cover site and no YUME-shaped response.

yumed ends the tunnel, so it knows which client connected and where its traffic goes. HTTPS inside the tunnel keeps page content between the app and the site, as it does on any network. The threat model shows what each party can see, and the stealth model covers the browser profile and the captures behind it.

Build, provision, connect

The quick start walks through these steps. Credentials are owner-only files, and a client bundle must move to its machine through a trusted channel.

01

Build

Clone the tree and run ezbuild.sh.

02

Provision

yume-setup writes a server and client kit: identities, access PSK, admission key, TLS material, configuration, and a cover site.

03

Serve

yumed serves the cover site and the authenticated tunnel on one listener.

04

Connect

The client offers SOCKS5, local forwards, or a managed Linux TUN.

Build

git clone https://github.com/FixCraft-Inc/yume.git
cd yume
./ezbuild.sh

Provision

./build/bin/yume-setup init \
    --host yume.example.com --port 8443 \
    --output ~/yume-kit --client-name laptop

Server

./build/bin/yumed --config ~/yume-kit/server/yumed.json --validate
./build/bin/yumed --config ~/yume-kit/server/yumed.json

Client

./build/bin/yume --config ~/yume-kit/client/yume.json
curl --socks5-hostname 127.0.0.1:1080 https://example.com/

Before you open a server to the public, give it your own cover site and a certificate for its domain. The operations guide lists what to publish to its users.

Port 443 needs CAP_NET_BIND_SERVICE, which the packaged service grants and nothing more. Cloudflare in HTTP mode terminates TLS and breaks YUME. Use Spectrum or another TCP passthrough if you front the daemon with it.

Verify release files

Published artifacts carry SHA-256 sidecars, an aggregate SHA256SUMS.txt, and a machine-readable manifest. Detached GPG signatures are attached when signing secrets are configured, and the workflow verifies each signature before uploading it.

Checksums

Verify with the per-artifact .sha256 file or the aggregate list.

Aggregate
sha256sum -c SHA256SUMS.txt

Signatures

Signed builds ship .sig sidecars for both artifacts, the checksum list, and the manifest.

GPG
gpg --verify yumed-amd64-linux.sig yumed-amd64-linux

Manifest

release-manifest.json records each artifact's component, OS, architecture, size, linkage, and SHA-256. Signatures travel in the .sig sidecars.
